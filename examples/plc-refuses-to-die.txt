title: Why the PLC Refuses to Die
speakers:
  MAYA: serena, curious and quick to react
  THEO: aiden, calm explainer with a dry sense of humor
---
MAYA: Okay, so I want to start with a little confession.
THEO: (over) Oh no.
MAYA: For years, I genuinely thought the PLC was a dinosaur. Like, a grey box bolted inside a cabinet, running code that looks like... a circuit diagram from the sixties.
THEO: [laughs] I mean, to be fair, that is kind of exactly what it is.
MAYA: Right! But here's the thing. We have cloud everything, AI everything, and that grey box is still running most of the factories on the planet.
THEO: It really is. Car plants, water treatment, the bottling line for whatever you drank this morning.
MAYA: So today, the question is: why? Why won't the PLC die?
THEO: And honestly, to answer that, you have to go back to the problem it was invented to solve.
MAYA: Which was?
THEO: Relays. Rooms full of relays. (slow) Thousands of them.
MAYA: (over) Huh.
THEO: So picture an auto plant in the late sixties. All the machine logic, the "if this switch closes, start that motor" stuff, is built out of physical relays and wires. And every model year, when the car changes...
MAYA: You rewire the whole thing.
THEO: You rewire the whole thing. Weeks of electricians tearing out panels.
MAYA: That sounds like a nightmare.
THEO: It was. So in nineteen sixty-eight, the Hydramatic division of General Motors writes up a spec. Basically: give us a machine that does what relays do, but you change it with software instead of a screwdriver.
MAYA: And somebody actually built it.
THEO: A small firm called Bedford Associates, with an engineer named Dick Morley. Their machine was the Modicon zero eighty-four.
MAYA: Zero eighty-four. Like... the eighty-fourth project?
THEO: Pretty much, yeah. Not exactly a marketing department.
MAYA: [laughs] Okay, but this is where the ladder logic thing comes in, right?
THEO: Exactly. And this is the part people miss. Ladder logic wasn't designed for programmers.
MAYA: (over) Right.
THEO: It was designed for electricians. It looks like a relay drawing on purpose. Two vertical rails, rungs across, contacts and coils. Someone who'd spent ten years reading relay schematics could walk up to it and just... read it.
MAYA: (thoughtful) So it's not old-fashioned. It's a user interface decision.
THEO: That's a great way to put it. And it still pays off. When a line goes down at three in the morning, the person next to the machine with a laptop is usually a maintenance tech, not a software engineer. They go online with the controller, watch the rungs light up live, and see which contact isn't closing.
MAYA: Okay, that's actually really compelling. But let me push on the computer part, because a PLC is a computer. Why not just run a regular PC?
THEO: So that comes down to one word. Determinism.
MAYA: Determinism.
THEO: A PLC runs what's called a scan cycle. Read every input. Solve the program, top to bottom. Write every output. Then do it again. Every few milliseconds, the same way, forever.
MAYA: And a PC can't do that?
THEO: A PC can do it most of the time. And "most of the time" is the problem. If your laptop stutters for half a second because it's installing an update--
MAYA: --you get a spinning wheel.
THEO: You get a spinning wheel. If a machine controller stutters for half a second, a conveyor overruns, a robot misses its mark, and you're scrapping parts. Or worse.
MAYA: (soft) Yeah. Okay. That reframes it.
THEO: And PLCs actually enforce this. There's a watchdog timer. If a scan takes longer than it's allowed to, the controller faults and puts its outputs in a safe state, instead of quietly running late.
MAYA: So it would rather stop than be wrong.
THEO: Right. And then add the physical stuff. They're built for heat, vibration, electrical noise, dusty cabinets. Vendors support a model for ten, twenty years. There are controllers from the eighties still running production lines today.
MAYA: Which, from an IT perspective, is horrifying.
THEO: [laughs] From an IT perspective, sure. From a plant manager's perspective, it's the dream. It just... works.
MAYA: Okay, so that's the case for the box. But I keep reading about virtual PLCs, and software-defined automation. Isn't that the thing that finally kills it?
THEO: (thoughtful) This is where it gets interesting. [pause 0.5] Because the honest answer is, it changes where the PLC lives, more than whether it exists.
MAYA: Say more.
THEO: A virtual PLC is the same control logic, the same scan cycle, but running as software on industrial servers, with a real-time operating system or hypervisor underneath to keep the timing tight. The big vendors have versions out now, and some large manufacturers are piloting them.
MAYA: And the pitch is, what, you manage controllers like you manage servers?
THEO: Exactly that. Backups, version control, updates, spinning up a new controller in minutes instead of ordering hardware. Everything IT has had for twenty years.
MAYA: But the wiring still has to be physical, right? Somebody still has to wire the sensor.
THEO: (emphatic) Always. The sensors, the motors, the safety circuits, those stay right next to the machine. What moves is the brain.
MAYA: So what I'm hearing is, the PLC isn't dying. It's... dissolving into the network a bit.
THEO: I like that. And there's a language standard that helps. IEC sixty-one one thirty-one, part three, from the early nineties. It defines the standard PLC languages. Ladder, function block diagram, sequential function charts, and structured text, which looks a lot like Pascal.
MAYA: (over) Mm-hmm.
THEO: So the logic people write today can, at least in principle, move from a box to a server without starting over.
MAYA: "In principle" is doing a lot of work in that sentence.
THEO: [laughs] It is doing a lot of work. Every vendor has its own flavor. Portability is better than it was, but it's not copy and paste.
MAYA: Okay, let's land this. Say someone listening is a software developer who just walked into their first plant--
THEO: --and they're horrified by the ladder logic.
MAYA: [laughs] And they're horrified. What should they take away?
THEO: That the PLC is a set of promises, not a box. The same answer, on time, every time, readable by the person who has to fix it at three in the morning. Whatever replaces the box has to keep every one of those promises.
MAYA: (thoughtful) The same answer, on time, every time. [pause 0.4] Honestly, a lot of software could learn from that.
THEO: (dry) Some of my web apps, definitely.
MAYA: [laughs] Okay. That's our episode. Thanks for listening.
